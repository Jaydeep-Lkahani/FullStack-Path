## Stage 3: Show the current weather

Add a second query hook, `useForecast(city, unit)`, to `src/queries.ts`. Think about the query key first: the request depends on the coordinates **and** the unit, so all three belong in the key (lesson 15). Then write `src/weatherCodes.ts` with `describeWeather(code)`, which turns Open-Meteo's weather code (a WMO number: 0 is clear sky, 61 is light rain, listed in the [forecast docs](https://open-meteo.com/en/docs)) into a `{ label, icon }`. In `App`, render `CurrentWeather` with `unit="celsius"` when a city is chosen, instead of the line from Part 1.

```tsx
// src/CurrentWeather.tsx
import type { City, Unit } from "./api";
import { cityLabel, formatTemp } from "./format";
import { useForecast } from "./queries";
import { describeWeather } from "./weatherCodes";

type Props = { city: City; unit: Unit };

export function CurrentWeather({ city, unit }: Props) {
  const { data, isPending, isError, error, refetch } = useForecast(city, unit);

  if (isPending) return <p role="status">Loading weather for {city.name}…</p>;
  if (isError) {
    return (
      <p role="alert">
        Could not load the weather: {error.message}{" "}
        <button onClick={() => refetch()}>Try again</button>
      </p>
    );
  }

  const { current } = data;
  const { label, icon } = describeWeather(current.code);
  return (
    <section aria-label={`Weather in ${city.name}`}>
      <h2>{cityLabel(city)}</h2>
      <p>
        <span aria-hidden="true">{icon}</span> {label}
      </p>
      <p>{formatTemp(current.temperature)}</p>
      <p>Feels like {formatTemp(current.feelsLike)}</p>
      <p>Humidity {current.humidity}%</p>
      <p>Wind {Math.round(current.windSpeed)} km/h</p>
    </section>
  );
}
```

## Stage 4: Forecast and units

Three changes, and the last one hides a trap.

1. **Daily forecast.** Write `DailyForecast({ days })`, a list with one item per day: weekday, icon and description, high / low, and the chance of rain when it is not `null`. Add `formatDay(date)` to `format.ts`. The API gives `"2026-10-20"`, a date with no time zone, and `new Date("2026-10-20")` means midnight **UTC**, which is still the day before for a visitor west of Greenwich. Format it with `Intl.DateTimeFormat` and `timeZone: "UTC"` to get the same weekday for everyone.
2. **Unit switch.** Write `UnitToggle` like the filter buttons in the todo app: two buttons in a `role="group"`, `aria-pressed` on the active one. Keep `unit` in `useState` in `App` and pass it down.
3. **No blank flash.** When the unit changes, the query key changes, so `isPending` is `true` again and the weather disappears until the new numbers arrive. TanStack Query's `placeholderData: keepPreviousData` keeps showing the old result meanwhile, and `isPlaceholderData` tells you it is not the final answer. Add it to `useForecast`, and show "Updating…" in `CurrentWeather` while `isPlaceholderData` is true.

Before you open the solution, predict what happens with `keepPreviousData` when the user searches for "Paris" **while Berlin is on screen** and picks it. Then try it.

<Solution>

```ts
// src/format.ts - add
// "2026-10-20" is a calendar date with no time zone. Reading and formatting it as UTC
// keeps the weekday the same for every visitor.
export function formatDay(date: string) {
  return new Intl.DateTimeFormat("en", { weekday: "short", timeZone: "UTC" }).format(
    new Date(date),
  );
}
```

```tsx
// src/DailyForecast.tsx
import type { Forecast } from "./api";
import { formatDay, formatTemp } from "./format";
import { describeWeather } from "./weatherCodes";

export function DailyForecast({ days }: { days: Forecast["days"] }) {
  return (
    <ul aria-label="5-day forecast">
      {days.map((day) => {
        const { label, icon } = describeWeather(day.code);
        return (
          <li key={day.date}>
            <strong>{formatDay(day.date)}</strong> <span aria-hidden="true">{icon}</span>{" "}
            {label}, {formatTemp(day.max)} / {formatTemp(day.min)}
            {day.rainChance !== null && `, ${day.rainChance}% rain`}
          </li>
        );
      })}
    </ul>
  );
}
```

**The trap:** `keepPreviousData` keeps the previous result for _any_ key change, not only for the unit. Without `key={city.id}`, picking Paris while Berlin is on screen showed the heading "Paris" above Berlin's temperatures, with "Updating…" beside them, until Paris's data arrived. The heading comes from the new `city` prop, and the numbers from the old cache entry, so the screen lies for a moment. Giving `CurrentWeather` a `key` that changes with the city makes React throw away the old component and start a new one, which has no previous data to keep, so it shows "Loading weather for Paris…". A unit switch keeps the same `key`, so it still keeps the old numbers. Part 3 has a test for this.

## Stage 5: Remember the last city

Save the city and the unit in `localStorage`, following the todo app's Stage 5. Create `src/storage.ts` with `loadSettings()` and `saveSettings(settings)`, under a versioned key such as `weather-v1`. Two rules apply again: saved data is **untrusted**, and storage can throw. This time you already have a validation tool: reuse `CitySchema` from `api.ts` and build a Zod schema for the whole settings object (`city` can be `null`, `unit` is one of the two units). `loadSettings` parses the saved JSON and falls back to the defaults (no city, Celsius) on any error. In `App`, keep `city` and `unit` together in one `useState(loadSettings)`, which reads storage once, and save in an effect whenever the settings change.

<Solution>

```ts
// src/storage.ts
import { z } from "zod";
import { CitySchema } from "./api";

const KEY = "weather-v1";

const SettingsSchema = z.object({
  city: CitySchema.nullable(),
  unit: z.enum(["celsius", "fahrenheit"]),
});
export type Settings = z.infer<typeof SettingsSchema>;

const DEFAULTS: Settings = { city: null, unit: "celsius" };

// Saved data is untrusted: parse it, and fall back to the defaults if anything is off.
export function loadSettings(): Settings {
  try {
    return SettingsSchema.parse(JSON.parse(localStorage.getItem(KEY) ?? "null"));
  } catch {
    return DEFAULTS;
  }
}

export function saveSettings(settings: Settings) {
  try {
    localStorage.setItem(KEY, JSON.stringify(settings));
  } catch {
    // storage full or blocked: the app keeps working without saving
  }
}
```

```tsx
// src/App.tsx
import { useEffect, useState } from "react";
import { CitySearch } from "./CitySearch";
import { CurrentWeather } from "./CurrentWeather";
import { loadSettings, saveSettings } from "./storage";
import { UnitToggle } from "./UnitToggle";

export default function App() {
  const [settings, setSettings] = useState(loadSettings);
  const { city, unit } = settings;

  useEffect(() => saveSettings(settings), [settings]);

  return (
    <main>
      <h1>Weather</h1>
      <CitySearch onSelect={(city) => setSettings((s) => ({ ...s, city }))} />
      <UnitToggle unit={unit} onChange={(unit) => setSettings((s) => ({ ...s, unit }))} />
      {city ? (
        <CurrentWeather key={city.id} city={city} unit={unit} />
      ) : (
        <p>Search for a city to see its weather.</p>
      )}
    </main>
  );
}
```

`useState(loadSettings)` passes the function itself, so React calls it once, on the first render, and not on every render. One schema now checks both the API's answer and the saved data, so a city that was saved by an older version of the app, or edited by hand to `{"name": 42}`, is rejected in the same way. The saved city is complete (name, coordinates, country), so on the next visit the weather loads immediately, with no search. In the sandbox, choosing Berlin, switching to °F and reloading brought back "Berlin" with 49°.

</Solution>
